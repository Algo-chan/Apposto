# Customer Mini App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Admins add item photos and shop banners by sending them to the bot (Step A). Customers
then order inside a Telegram Mini App: shops, then menu with photos, then basket and details,
then confirm, then pay (Step B).

**Architecture:**
- The existing Render HTTP server, which today serves only `/health`, gains a small router:
  - `/img/:fileId` proxies Telegram photos, with a cache;
  - `/api/*` is a JSON API, authenticated by Telegram's signed `initData`;
  - `/app/*` serves static plain-JS front-end files from `webapp/`.
- Chat ordering and the API share one module, `checkoutFlow`, so both send identical
  shop, dispatch and tracker messages.
- Photos are stored as Telegram `file_id`s in two new sheet columns.

**Tech Stack:**
- Back end: Node ≥ 20 (ESM), grammY, google-spreadsheet, `node:http` and `node:test`. No new
  npm dependencies.
- Front end: vanilla HTML/CSS/JS plus `https://telegram.org/js/telegram-web-app.js`.

**Spec:** `docs/superpowers/specs/2026-11-10-mini-app-design.md`

## Global Constraints

- No new npm dependencies. The front end has no framework and no build step.
- Never start the bot locally with the live token (it runs on Render). The tests and
  `scripts/preview-app.js` use fake tokens and fake Telegram APIs only.
- Never use unquoted heredocs containing backticks in shell commands. That once ran
  `npm run setup-sheet` against the live sheet.
- Texts:
  - user-facing texts come in om/am/en;
  - new om/am strings get the same "native speaker review" note as `src/i18n.js`;
  - admin-only replies are English.
- Limits (the same as chat):
  - item quantity is 1–20;
  - the special request is `cleanText(…, 300)`;
  - the landmark is `cleanText(…, 200)` and at least 3 chars.
- The app URL is `APP_URL` env, else `${RENDER_EXTERNAL_URL}/app`, else empty. When it is empty,
  no app buttons are shown.
- `initData` max age: 24 h (86400 s).
- Idempotency window for `requestId`: 10 minutes.
- Status screen poll: every 5 s.
- Photo sizes: items use the largest `PhotoSize` with width ≤ 800, banners ≤ 1280. With none
  that small, take the smallest.
- Photo cache: an in-memory LRU of 30 MB total. One file is at most 5 MB. Header:
  `Cache-Control: public, max-age=31536000, immutable`.
- JSON body limit: 16 KB.
- API errors are `{ "error": "<CODE>" }`, with these HTTP statuses:
  - 400: `BAD_REQUEST`, `BAD_PHONE`, `BAD_LANDMARK`, `EMPTY`, `BAD_REF`;
  - 401: `UNAUTHORIZED`;
  - 404: `NOT_FOUND`;
  - 409: `SHOP_CLOSED`, `ITEM_GONE`, `OUT_OF_RANGE`, `BAD_TRANSITION`, `DUPLICATE_REF`;
  - 500: `ERROR`.

## Review Focus

1. **Concurrent double Confirm.** Two `POST /api/orders` with the same `requestId` arrive at the
   same time, not one after the other. Expected: exactly one order. The test goes in Task 6.
2. **The price changed or the item was turned off while the basket was open.** Expected: the
   server uses today's sheet price, or rejects with `ITEM_GONE`. It never uses the page's price.
   The test goes in Task 6.
3. **Messy captions:** `i1`, `  banner m1 `, `BANNER M1`. Expected: they work. The test goes in
   Task 2.
4. **An app-placed order paid by typing the ref in the chat** instead of in the app. Expected:
   it works as for chat orders. The test goes in Task 5.
5. **The server is asleep or returns a 5xx when the app opens.** Expected: "Connecting…" and
   retries, then an error with Retry, never a blank page. The test is `requestWithRetry` in
   Task 9.

**Files:**

**Interfaces:**
- Produces:
  - `verifyInitData(initData: string, botToken: string, { maxAgeSec = 86400, now = Date.now() } = {}) -> { user: { id: string, firstName: string, lastName: string, languageCode: string } } | null`
  - `signInitData(fields: object, botToken: string) -> string` is a test and preview helper that
    builds a valid string.
  - The algorithm is Telegram's WebApp validation:
    - `secret = HMAC_SHA256(key="WebAppData", msg=botToken)`;
    - the check string is all pairs except `hash`, sorted by key, as `key=value` joined by `\n`;
    - `hash = hex(HMAC_SHA256(secret, check))`;
    - compare with `crypto.timingSafeEqual`;
    - reject when `now/1000 - auth_date > maxAgeSec`, or when `user` is missing or isn't JSON.

### Task 6: Web API routes

**Files:**
- Create: `src/web/api.js`
- Test: `test/api.test.js`

**Interfaces:**
- Consumes:
  - `checkout` (Task 5) and `insights.eta`/`insights.prepMinutes`;
  - `roadDistanceKm`, `calcDeliveryFee`, `normalizePhone`, `normalizeRef`, `cleanText`,
    `summarizeCart`, `FINAL`, `STATUS`;
  - `merchantAccountsHtml` is not used. The API returns raw fields.
- Produces:
  - `createWebApi({ store, config, insights, checkout, now = () => Date.now() })` returns
    `{ handle(method, path, { user, body }) -> Promise<{ status: number, body: object }> }`.
  - `user` is the verified `initData` user. The HTTP layer (Task 7) does the auth.
  - `imgUrl(fileId)` is `fileId ? `/img/${fileId}` : null`.

| Route | Response body |
|---|---|
| `GET /api/me` | `{ lang: string \| null, phone: string, openOrderId: string \| null }`. The open order is the newest non-final order of this customer. |
| `POST /api/lang {lang}` | `{ ok: true }`. Saves `{id, name, lang, createdAt if new}`. Bad lang gives `BAD_REQUEST`. |
| `GET /api/shops` | `{ shops: [{ id, names, prepMin, banner }] }`. Active shops only. |
| `GET /api/shops/:id/menu` | `{ shop: {id, names, banner}, items: [{ id, names, price, photo }] }`. An inactive or missing shop gives `SHOP_CLOSED`. |
| `POST /api/quote {merchantId, lat?, lng?}` | `{ distanceKm, deliveryFee, serviceFee, outOfRange, eta }`. With no lat/lng: base fee, `distanceKm: null`. |
| `POST /api/orders {requestId, merchantId, items, custom?, lat?, lng?, landmark, phone}` | `{ orderId }` |
| `GET /api/orders/:id` | `{ id, status, shopName, lines: [{name, qty, subtotal}], custom, foodTotal, deliveryFee, serviceFee, eta, pay, rider }` |
| `POST /api/orders/:id/ref {ref}` | `{ status }`. Errors: `BAD_REF`, `DUPLICATE_REF`, `BAD_TRANSITION`, `NOT_FOUND`. |

`POST /api/orders` works like this:
- It rebuilds the order from the store.
- An unknown item id or an inactive item gives `ITEM_GONE`, and quantities are clamped to 1–20.
- It calls `checkout.placeAndNotify(...)` with `customer.name` from the user's first and last
  name, and with `lang` from Customers, else `'en'`.
- `requestId` must match `/^[A-Za-z0-9-]{8,64}$/`. The idempotency map is keyed
  `${user.id}:${requestId}` and stores the in-flight promise, so concurrent repeats share it.
  Entries are pruned after 10 minutes.

In `GET /api/orders/:id`:
- `pay` is `{ amount: foodTotal, telebirr, cbeAccount, accountName, phone }`, only when the
  status is not PLACED, REJECTED or CANCELLED.
- `rider` is `{ name, phone }` once `riderId` is set, else null.
- Another customer's order gives `NOT_FOUND`.

Errors: any route that throws an unknown error gives 500 `ERROR` and logs it. `OrderError`s map
to their codes.

      "Connecting…". 4xx is returned at once, never retried.

    - `index.html` is served with `<script>window.__DEV_INIT_DATA__="…"</script>` injected,
      built with `signInitData` for user 100.

Screens follow spec Part 1, in this order: language (if `me.lang` is null), Shops, Menu, Basket &
details, Check & confirm, Status. Some behaviours to pin:

  Continue / Confirm order / Send).
- Theme: `var(--tg-theme-bg-color)` etc., with fallbacks.
